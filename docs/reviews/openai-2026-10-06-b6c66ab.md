Major, lib/ldap_sync/infectors/auth_source_ldap.rb:321
Dynamic groups freshness logic inverted under rake
- Problem: dyngroups_fresh? now returns !!dyngroups_updated? when running_rake? is true. Previously it returned !dyngroups_updated?. This flips the semantics of “freshness” for a rake run. Depending on how dyngroups_fresh? is consumed (to decide whether to refresh or skip), this will either:
  - re-compute dynamic group sets on every use within a single rake run (potentially O(N) redundant LDAP queries/users), or
  - skip the first required refresh and operate with stale/empty data until dyngroups_updated? is set elsewhere.
- Failure scenario: With dynamic groups enabled (no TTL), run rake redmine:plugins:ldap_sync:sync_users on a large directory. On the first run of the process, dyngroups_updated? is false. With the new code dyngroups_fresh? returns false where callers expect true to mean “fresh,” causing dynamic group resolution to be performed repeatedly per user (or, if the caller uses unless, skipped once at startup). Result: either massive LDAP load/Nx slowdown or missing dynamic memberships in that run.
- Fix: Restore the original logic for rake runs so that “fresh” reflects “already updated in this process”:
  - def dyngroups_fresh?; if running_rake?; !dyngroups_updated?; else … end
  - Add a unit test exercising a rake run with dynamic groups that asserts only one refresh happens and memberships are present.

Resolution: not a bug, no change to the logic; test added in the next commit. The callers are `reload_dyngroups! unless dyngroups_fresh?` and `update_cache: !dyngroups_fresh?`, so "fresh" must mean "already loaded in this run": the first call loads (dyngroups_updated nil -> not fresh), update_dyngroups_cache! sets dyngroups_updated, every later call uses the cache. The old `!dyngroups_updated?` never loaded in a new rake process (b82b6e4). New test "#sync_groups and #sync_users should load the dynamic groups once per rake run": exactly 1 load and the dynamic memberships present; it fails with the old logic (0 loads).

Major, lib/tasks/ldap_sync.rake:61 and lib/ldap_sync/dry_run.rb:8 (cross-cutting)
DRY_RUN still mutates caches (Rails.cache and file cache), breaking “no changes” guarantee
- Problem: DRY_RUN is now implemented by wrapping the sync in a DB transaction and raising ActiveRecord::Rollback. This does not roll back side-effects outside the database:
  - Rails.cache entries (dyngroups state/TTL) are written in AuthSourceLdap (e.g., dyngroups_state_key) and will persist.
  - File-based caches under tmp/ldap_cache (used for nested/dynamic groups) are written (FileStore), unaffected by the DB rollback.
  As a result, a DRY_RUN warms or alters caches and may change behavior of the next real run (e.g., skip dynamic groups recomputation as “fresh”, or use stale nested-group results).
- Failure scenario: Run DRY_RUN=1 rake redmine:plugins:ldap_sync:sync_all with dynamic groups enabled and TTL configured. Immediately run the real sync_all. The second run treats dyngroups as fresh due to the cached state set by the dry run and skips recomputation, leaving memberships inconsistent with LDAP.
- Fix:
  - Provide a dry-run guard that prevents cache writes during DRY_RUN, e.g., a process-local flag LdapSync::DryRun.active? checked around all cache mutations (Rails.cache.fetch/write, FileStore writes). Or:
  - Ensure cleanup after the dry-run wrapper: in run_ldap_sync, when DRY_RUN is set, after LdapSync::DryRun.without_changes returns, clear caches:
    - Rails.cache.delete(dyngroups_state_key) and reset AuthSourceLdap.dyngroups_updated = false
    - FileUtils.rm_rf(Rails.root.join('tmp/ldap_cache'))
  - Add a test asserting that counts stay the same and caches (Rails.cache and tmp/ldap_cache) are unchanged/cleared after DRY_RUN.

Resolution: not changed. There is no Rails.cache use in the plugin (no dyngroups_state_key); the only caches are the FileStores under tmp/ldap_cache (nested groups closure, dynamic groups), filled with what LDAP returns at that moment, the same data a real run writes. A rake run reloads the dynamic groups once per process whatever the cache says (dyngroups_updated is process-local), so a dry run cannot make the next real run skip them. A dry run can refresh these caches for web logins with current LDAP data; that is no change to Redmine data. Recorded in docs/REDMINE7-MIGRATION.md.

- Problem: Selectors like #admin-menu a.ldap-sync:not(:has(svg)) and .icon-disable:not(:has(svg)) depend on :has(), which is not supported in several browsers (e.g., Firefox ESR). On those browsers, the selector is dropped entirely; if Redmine < 6 (no sprite_icon) or sprite loading fails, the admin tile and enable/disable links may render with no icon or with a tiled background.
- Failure scenario: On Redmine 5.1 in Firefox ESR, open Administration. The “LDAP synchronization” tile shows no icon (or a tiled PNG) because :has() isn’t honored, and the CSS fallback rules don’t match; enable/disable buttons may also miss their images.
- Fix: Avoid :has() for fallbacks. For pre-6 Redmine, always apply the background-image with explicit background-repeat: no-repeat; background-position and padding-left on the .icon-* classes (and the admin tile class). For 6+, rely on sprite_icon; no need for :has() detection.

Resolution: fixed in the next commit. No :has() any more: on Redmine 6+ the links get the SVG icon and only the class "icon"; on Redmine < 6 they get the plugin's CSS classes (icon-ldap-sync, icon-enable, icon-disable) with the PNGs, as before. Helper test checks the class per version; e2e run on 7.0 and 5.1 (menu and list as before on 5.1).
